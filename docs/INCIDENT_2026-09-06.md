# Incident: 2026-09-06 Sunday maintenance

## Source of observations

Operator-provided updater and post-update/log-doctor reports. This document intentionally separates observed facts from hypotheses.

## Observed

- maintenance started around 02:20 CEST;
- cleanup succeeded and reported ~5.2 GB reclaimed;
- 13 APT packages were updated successfully;
- Docker main `up` phase returned failure;
- the updater log did not preserve the concrete error text needed for root-cause analysis;
- CV stack was skipped after the main failure under current policy;
- reboot was blocked by the updater error; later verification reported that no reboot was required;
- post-update verification found 20/20 containers up and local/public checks healthy, including HA/Grafana/AdGuard/Prometheus/Hermes dashboard;
- `balkons-log.service` restarted roughly 230 times while Mosquitto was unavailable and later recovered;
- CV stats, Hermes HA adapter and Uptime Kuma saw transient dependency failures and recovered;
- Hermes application logs were otherwise clean; Hermes source was reported far behind origin/main but manual update is by design.

## Not proven

The report mentioned a large Home Assistant image pull. Without the missing Compose stderr, the image size, timeout, resource pressure or another cause cannot be asserted as the root cause.

## Design consequences

1. Never discard exact stderr/timeout reason from mutating commands.
2. Separate command failure from final system health.
3. Add per-stack transaction/evidence records.
4. Prevent planned dependency downtime from creating restart storms.
5. Make CV continuation depend on the shared failure domain, not only `main` exit code.
6. Keep the verifier/doctor layer, but constrain remediation to explicit playbooks.

This incident is a mandatory regression scenario before the redesigned updater is considered stable.
