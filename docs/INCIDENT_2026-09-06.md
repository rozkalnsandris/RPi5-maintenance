# Incident: 2026-09-06 Sunday maintenance

## Evidence sources

This incident record separates observed facts from the reconstructed failure path. Evidence comes from the updater log, `rpi5-update.service` journal, `docker.service` journal, APT/dpkg history and read-only container metadata inspected on 2026-09-06.

## Observed

- maintenance started at about 02:20 CEST;
- cleanup succeeded and reported about 5.2 GB reclaimed;
- APT upgraded 13 packages between about 02:20:32 and 02:21:09;
- the APT transaction included `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-compose-plugin`, `docker-buildx-plugin` and `docker-ce-rootless-extras`;
- `docker.service` stopped at about 02:20:43 and completed restart/initialization at about 02:21:03;
- `mosquitto` did not return to running state during the Docker main transaction; the Docker journal records failed exec attempts against the stopped container through 02:22:06;
- the main candidate pull continued after the daemon restart and recorded successful pulls, including Grafana at about 02:21:54 and Home Assistant at about 02:22:01;
- at 02:22:06 the updater marked the main Docker transaction failed and skipped CV under the then-current policy;
- the updater log contains no actionable post-pull phase/reason between the completed pull and the main failure;
- local/public HTTP checks later in that run were green, but those checks did not prove every Compose container was running;
- reboot was blocked because the updater had an error; a later read-only check found no current reboot-required marker;
- `mosquitto` container metadata records a later start around 02:41 CEST, after the updater had already exited.

## Reconstructed failure path

The extracted V27 source has a post-pull target-selection path that requires each registry-backed service to have a running Compose container. A stopped service makes `docker compose ps -q <service>` return no container ID; the selector then returns `2`. V27 propagated that result as a generic Docker failure without recording the selector reason or service.

The 2026-09-06 stopped `mosquitto` state therefore reproduces a concrete source path consistent with the observed timing: APT restarts Docker, one service remains stopped, candidate pulls finish, target selection fails before reconcile and the updater reports only `Docker main: ❌`.

This is the leading evidence-backed reconstruction, not proof of the exact historical return statement: V27 did not retain the required structured phase record.

## Design consequences

1. Preserve exact Docker command output and exit/timeout status.
2. Record post-pull target-selection failures with a stable reason and service identity.
3. Preserve immutable image/container state before and after the Docker transaction.
4. Distinguish pull, target-selection, reconcile, readiness and rollback evidence.
5. Verify final Compose health independently from HTTP endpoint health.
6. Keep mutation evidence separate from final system health.
7. Do not add automatic remediation until the failure evidence is reviewable and deterministic.

This incident is a mandatory regression scenario for the P1 evidence-hardening milestone.
